# Дизайн: маршрутизация моделей и HTML-редактор

Дата: 2026-10-22
Статус: исторический дизайн исходной реализации. Базовая схема и редактор реализованы,
затем расширены native-адаптерами, параметрами провайдеров, backup/откатом и диагностикой.
Актуальное устройство, ограничения и результаты проверок описаны в [README](../../../README.md).
Фразы «сейчас» и выводы о relay.fast ниже относятся к моменту подготовки дизайна.

## Задача

Сейчас маршрутизация живёт прямо в `litellm-config.yaml`: пять алиасов, у каждого
свой `api_base`, fallback-цепочки дописаны руками. Из-за этого:

- непонятно, какой алиас кто обслуживает и куда он уезжает при падении;
- чтобы добавить модель, надо помнить формат YAML и не сломать остальное;
- нет способа сказать «сначала этот провайдер, потом другой, и только потом
  другая модель» — LiteLLM умеет это через `order`, но в конфиге он не задан;
- ошибки маршрутизации видны только в логах LiteLLM, а разобрать их мешает шум:
  за последний запуск 1107 строк из 4892 — ожидаемые 404/429 от `CountTokens`.

Цель: одно место, где описано «кто за чем» и «если упал, то куда», страница, где
это правится без знания YAML, и генератор, который ставит `litellm-config.yaml`
из этого описания.

## Что выяснено про relay.fast

Зеркального домена в документации нет. Проверены `llms.txt`, `llms-full.txt`,
`/reference/api.md`, страница `/routing`, плюс DNS-проба вероятных имён
(`api.`, `mirror.`, `alt.` — не отвечают).

Что есть на стороне relay.fast:

| Механизм | Где | Что делает |
| --- | --- | --- |
| Keys page | кабинет | несколько ключей на аккаунт |
| Routing page | кабинет | какой *source* обслуживает модель — для аккаунта или ключа |
| Model mapping | `/model-mappings` | правила «запрос A обслуживается моделью B», до 20, цепочки A→B→C |

Отсюда два следствия. Первое: «зеркало» делается на стороне LiteLLM, а не
вторым доменом — один алиас описывается несколькими деплойментами с разными
`order`. Второе: реальная избыточность, доступная сегодня, — это **второй ключ
relay.fast на том же хосте**, поэтому деплоймент должен уметь задавать свой
`key_env`. Когда появится настоящий зеркальный хост, он добавляется как ещё
один деплоймент со своим `base`.

## Как LiteLLM это делает

`order` в `litellm_params` задаёт приоритет внутри одной `model_name`. Меньше —
раньше. Проверено в исходниках 1.106.0:

- `router.py:7642` — «ORDER-BASED FALLBACKS: prepend higher order levels to the
  fallback list»: при падении деплоймента уровни с большим `order` подставляются
  в начало цепочки, и только после них идут внешние `fallbacks`;
- `router.py:13557` — фильтрация кандидатов до самого низкого здорового уровня
  `order`.

Схема получается ровно такая: провайдер → его второй ключ → следующий
провайдер → и только потом fallback на другую модель.

`enable_weighted_failover` **не используется**: по `router.py:1014` он работает
только при `simple-shuffle`, только в async-ветке и достигается лишь когда
уровень `order` в группе единственный (`router.py:7699`). В нашей топологии он
не делает ничего.

## Решение

### 1. `models.yaml` — источник правды

Единственное место, где описана маршрутизация. Ключей не содержит — только имена
переменных окружения.

```yaml
providers:
  relay-fast:
    key_env: RELAY_FAST_API_KEY
    chat_base: https://relay.fast/v1      # диалект openai
    messages_base: https://relay.fast     # диалект anthropic

timeouts:
  request: 120
  stream: 120
  total: 300
  retries: 1
  cooldown: 5

aliases:
  - name: kimi-k3
    deployments:
      - provider: relay-fast
        model: kimi-k3
        dialect: openai
        order: 1
      - provider: relay-fast
        model: kimi-k3
        dialect: openai
        order: 1
        key_env: RELAY_FAST_API_KEY_2   # второй ключ, тот же хост
      - provider: relay-fast
        model: kimi-k3
        dialect: openai
        order: 2
    fallbacks: [gpt-6-luna, deepseek-v4.1-flash]
    model_info:
      supports_function_calling: true
```

Поля:

- `providers[].key_env` — имя переменной окружения, не ключ.
- `providers[].chat_base` / `messages_base` — адрес под каждый диалект. Разделение
  нужно потому, что relay.fast требует `/v1` для [OI]-совместимых запросов и
  корень хоста для Anthropic.
- `deployments[].dialect` — `openai` или `anthropic`. Это **диалект апстрима**,
  а не протокол клиента: клиент может слать `/v1/messages` и к `openai`-модели,
  LiteLLM конвертирует сам.
- `deployments[].key_env` — необязательное переопределение ключа провайдера.
- `deployments[].order` — приоритет. **Одинаковые `order` разрешены**: LiteLLM
  трактует равные значения как один уровень и балансирует внутри него.
- `aliases[].fallbacks` — имена других алиасов, порядок важен.
- `aliases[].model_info` — метаданные для роутера, не уходят в запрос.

### 2. `render.py` — генератор

Читает `models.yaml`, проверяет и пишет `litellm-config.yaml`.

Проверки (при нарушении — ошибка с путём в YAML, конфиг не пишется):

- имя алиаса не пустое и не повторяется;
- `deployments` не пуст;
- `dialect` — только `openai` или `anthropic`;
- провайдер существует, у него заполнен base под нужный диалект;
- цель из `fallbacks` существует среди алиасов; алиас не ссылается сам на себя;
- в графе fallbacks нет циклов.

Генерация: на каждый деплоймент — запись в `model_list` с `model_name` из
алиаса, `model` = `<dialect>/<model>`, `api_base` из провайдера по диалекту,
`api_key: os.environ/<key_env>` (деплойментный, иначе провайдерный), `order`,
плюс `model_info` из алиаса.

Неизменяемая обвязка: `guardrails` (headroom, `pre_call`, `default_on`),
`litellm_settings` (`use_chat_completions_url_for_anthropic_messages: true`,
`drop_params: true`, `request_timeout` из `timeouts.request`),
`general_settings` (`disable_ui`, `master_key: os.environ/LITELLM_MASTER_KEY`),
`router_settings` — таймауты и `retries` из `models.yaml`, `retry_policy` без
изменений.

Запись атомарная: временный файл рядом, затем замена. При любой ошибке
существующий `litellm-config.yaml` остаётся нетронутым.

### 3. `editor.py` — локальный редактор

`python editor.py` поднимает сервер на `127.0.0.1:8788` и открывает браузер.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/` | HTML-страница |
| GET | `/api/config` | `models.yaml` как JSON |
| POST | `/api/config` | валидация и запись `models.yaml` |
| POST | `/api/render` | рендер `litellm-config.yaml` из текущего `models.yaml` |
| POST | `/api/apply` | render + перезапуск LiteLLM |
| GET | `/api/catalog` | прокси к `GET {chat_base}/models` провайдера |

`/api/catalog` берёт **первого по порядку объявления провайдера, у которого
задан `key_env` и переменная непустая**, и запрашивает у него `/models`. Если
такого нет — `400` с текстом «не задан ключ ни одного провайдера». Ошибка
апстрима возвращается как `502` с кодом и текстом, тело ответа не пробрасывается.

Страница:

- список алиасов; в каждом — деплойменты (провайдер, модель, диалект, порядок,
  ключ) и список fallbacks;
- «Добавить модель» открывает форму по шаблону: первый провайдер, `dialect:
  openai`, `order: 1`, остальные поля пустые;
- каждое поле помнит последнее введённое значение по ключу
  `<alias>.<field>` в `localStorage`, и рядом есть кнопка «вернуть сохранённое»,
  которая подставляет значение из файла на диске. Это две разные вещи: первое —
  «что я вводил в прошлый раз», второе — «что реально стоит сейчас»;
- провайдеры редактируются на отдельной вкладке: имя, `key_env`, `chat_base`,
  `messages_base`;
- `fallbacks` — список с подсказками из имён существующих алиасов;
- «Сохранить» пишет `models.yaml`; «Применить» пишет оба файла, перезапускает
  LiteLLM и показывает результат проверки health.

Ограничения, принятые осознанно:

- порт 8788 — рядом с 8001 (LiteLLM) и 8787 (Headroom);
- слушает только `127.0.0.1`; запросы с чужим `Host`/`Origin` отклоняются;
- поля для API-ключа в UI нет: ключи живут только в env;
- только стандартная библиотека, чтобы редактор работал в любом из двух venv.

### 4. Перезапуск

`start.ps1` получает параметр `-Restart`: останавливает только процесс LiteLLM
(Headroom от конфига не зависит) и поднимает его заново с проверкой health.
`editor.py` вызывает `start.ps1 -Restart` для `/api/apply`.

Перед стартом `start.ps1` рендерит конфиг, если рядом есть `models.yaml`. Если
его нет — работает как сейчас с готовым `litellm-config.yaml`. Ошибка рендера
останавливает запуск и не поднимает сервисы.

### 5. Тесты

Новые в `tests/`:

- валидатор отвергает дубль имени, неизвестную цель fallback, цикл, пустой
  список деплойментов, неизвестный диалект, отсутствующий base;
- рендер не содержит `sk-`;
- рендер идемпотентен: два прогона дают одинаковый файл;
- каждый алиас попадает в `model_list` ровно столько раз, сколько у него
  деплойментов;
- при ошибке валидации существующий `litellm-config.yaml` не меняется.

Правки существующих:

- `tests/test_setup.py::test_provider_routes` сейчас требует, чтобы все
  `api_base` были relay.fast — при втором провайдере это неверно. Тест
  переводится на проверку инвариантов (`openai`-диалект → base оканчивается на
  `/v1`, `anthropic` → без `/v1`), а не конкретных хостов;
- `smoke_check.py` читает `general_settings.master_key` и шлёт его как bearer.
  С `os.environ/...` он отправит литерал. Скрипт переводится на
  `os.environ.get` с тем же именем, а обход моделей — на уникальные
  `model_name`, чтобы не проверять один алиас по разу на деплоймент.

### 6. Миграция

Порядок:

1. `render.py` и схема `models.yaml`.
2. `tools/migrate_config.py` — одноразовый скрипт, читает текущий
   `litellm-config.yaml` и пишет `models.yaml`. Остаётся в репозитории, чтобы
   миграцию можно было повторить.
3. Приёмка — round-trip через нормализатор, а не побайтовое сравнение. Явный
   список допустимых различий: добавленный `order`, `master_key` из литерала в
   `os.environ/...`, переставленные ключи словарей. Всё остальное — расхождение
   и ошибка.
4. Тесты, `editor.py`, `start.ps1 -Restart`, README.

## Не-цели

- Не трогаем Headroom и его guardrail.
- Не вводим БД и не храним историю конфигураций: `git` уже даёт историю.
- Не делаем авторизацию в редакторе: он слушает только loopback.
- Не управляем аккаунтом relay.fast (ключи, sources, model mapping) через API —
  в документации такого API нет.
- Не лечим mid-stream ошибки: сбой после начала стрима прозрачно не
  восстанавливается, клиент повторяет ход целиком.

## Что осталось за исполнителем

- точная разметка и стили страницы;
- разбиение `editor.py` на модули, если файл перерастёт разумный размер;
- формат сообщений валидатора.
